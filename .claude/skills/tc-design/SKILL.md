# tc-design — 기획 문서 + 코드 → 실무 TC

입력 문서와 코드에서 **운영자 조작 하나에 TC 하나**를 뽑고, 실제 화면 캡처로 보이는 모양을 확인하고, 작성 맥락을 모르는 감사자 둘(소스 대조·수행)로 반증한 뒤, 검사기로 금지 패턴을 막는다. **소스는 동작 근거, 캡처는 보이는 모양 근거**다. 규칙 정본 = [`TC_QUICKSTART.md`](../../../TC_QUICKSTART.md). 이 파일은 순서만 정한다.

## 좋은 산출물이란 (품질 기준)

- 처음 보는 테스터가 **시트만 보고** 상태를 갖추고, 조작하고, 판정할 수 있다.
- 화면 문구는 코드·캡처의 **글자 그대로**(지어낸 문구 0). 기호 모양·위치·글자 유무는 캡처에서 확인한 것만.
- Pre/Step/Expected 에 `[확인 필요]` 0 — 못 찾은 것은 Comment 에만 있고, 판정 줄에서 빠져 있다.
- 행마다 자기완결 — 다른 행을 참조하지 않는다. 조건부 수행 규칙은 Pass/Fail/N/T 세 경우가 다 있다.
- 기획과 코드가 다른 곳은 Comment 에 「기획: … / 코드: …」로 드러나 있다. 한쪽으로 조용히 맞추지 않았다.
- 자동화용 기술 정보(응답 고정, 세는 횟수, 주소)는 시트가 아니라 **부록 note** 에 있다.
- Pre 가 Expected 가 기대는 상태(개수뿐 아니라 선택·완료·잠김 등)를 전부 적었다. 앞 TC 에서 이어 해도 Expected 가 선다.
- 반증 기록 두 갈래((a) 라운드별 ❌, (b) 라운드별 모호·불가·도구 한계와 Pre 반례 검사한 행 수)와 `tc_lint` 종료 코드 0 이 결과에 붙어 있다.

## 절차

1. **입력 받기** — 기획 세부 문서, 코드 위치(화면 템플릿·문구 리소스·**공용 스타일**·분기 로직), 티켓이 있으면 본문과 **코멘트 전부**. 코멘트가 본문보다 최신이다. 무엇을 어느 판으로 읽었는지 근거 목록에 적는다. 입력이 없으면 지어내지 말고 사용자에게 묻는다. 앱을 여는 방법(주소·실행 명령·장비)도 받는다.
2. **실행 화면 관찰** — 화면이 있는 앱이면 **초안 전에** 실제 화면을 열어 TC 를 쓸 화면·상태마다 캡처한다(`TC_QUICKSTART.md §1.1`). 컨트롤 모양(체크칸이 네모인지 기호 하나인지), 이름표 글자 유무, 누른 직후 테두리를 캡처에서 본다. 캡처 목록을 근거 목록에 넣는다. **못 열면** 그 사실과 이유를 결과 머리에 적고, 모양에 기대는 Expected 를 쓰지 않는다.
3. **화면 문구 목록 뽑기** — 코드의 문구 리소스와 템플릿 리터럴 **양쪽**에서 화면에 뜨는 문장·버튼 이름을 글자 그대로 모아 `screen-text.txt` 로 둔다(한쪽만 찾으면 「없음」으로 오판한다).
4. **초안** — 화면마다 운영자가 하는 조작을 나열하고 조작 하나에 TC 하나. 정상 경로 + 기획·코드의 예외 분기 + 경계값 + 돈·물건·안전에 닿는 것. 기획과 코드가 다른 곳은 이 단계에서 표시한다.
5. **문체 맞추기** — `TC_QUICKSTART.md §3` 칸 규칙. 기술 정보는 부록 note 로 옮긴다. 확정 전에 Pre/Step/Expected 의 `[확인 필요]` 를 해소하거나 Comment 로 옮기고, 다른 행 참조를 걷어 각 행에 직접 쓰거나 표 머리(Summary)로 올리고, 조건부 규칙에 Pass/Fail/N/T 를 다 적고, 눈대중 낱말을 비교 기준으로 바꾼다. 판정할 표시가 누른 직후 포커스 테두리와 헷갈리면 Step 에 「빈 곳을 눌러 포커스를 뺀다」를 넣는다.
6. **사람 말로 다시 쓰기** — `§4`. 화면 문구·숫자·고유명사 보존, 분량 75~110%.
7. **반증 라운드 두 갈래** — 브리핑은 [`references/AUDITOR_BRIEF.md`](references/AUDITOR_BRIEF.md) 를 그대로 쓴다. 작성 이유·가정·이 대화의 맥락은 넣지 않는다. 두 갈래는 서로 다른 새 서브에이전트로 병렬로 띄운다.
   - **(a) 소스 대조** — 결과 표 + 원본 소스 경로. 돌아온 지적은 원문을 다시 열어 맞는지 본 뒤 채택한다. 근거 줄이 없는 지적은 버린다.
   - **(b) 수행** — **결과 표만** + 앱을 여는 방법(못 열면 캡처 묶음). 소스·기획은 주지 않는다. 행마다 가능/모호/불가/도구 한계. 모호 = 읽는 법이 두 가지 이상, 한 번이라도 해석을 골랐으면 모호. **Pre 반례 검사 필수** — Pre 를 만족하는 다른 상태(앞 TC 에서 이어 온 상태 포함)를 하나 이상 만들어 Expected 가 그때도 서는지 본다. 불가 = 사람도 못 함, 도구 한계 = 사람은 되는데 자동 수행 도구가 못 만듦. 돌아온 지적은 화면을 다시 열어 맞는지 본 뒤 채택한다.
   - **종료 조건**: (a) ❌ 0 그리고 (b) 불가 0 그리고 모호 0. 도구 한계는 행 번호·이유를 결과 머리에 적고 사람 수행 대상으로 남긴다. 하나라도 남으면 고치고 두 갈래 모두 **새 에이전트로** 다시 돌린다(같은 에이전트에 「고쳤다」를 알리면 맥락이 샌다). 표가 크면 화면 단위로 갈라 병렬로 던진다.
   - 화면을 못 열어 (b) 를 못 돌렸으면 결과 머리에 「수행 반증 안 함 — 이유」를 적는다. (a) ❌ 0 만으로 「수행 가능」이라고 쓰지 않는다.
8. **금지 패턴 검사** — `python3 tools/tc_lint.py --self-test` 가 통과하는지 먼저 보고, `python3 tools/tc_lint.py <표> --screen-text screen-text.txt`. 종료 코드 1 이면 고치고 7 부터 다시(문장이 바뀌었으면 반증도 다시).
9. **결과표** — [`references/TEMPLATE.md`](references/TEMPLATE.md) 꼴로 낸다. 시트에 쓰라는 요청이 있으면 `TC_DESIGN_GUIDE.md §6` 서식으로.

## 언제 쓰지 말 것 (경계)

- 무엇을 테스트할지 아직 모름(커버리지 지도가 먼저) → `advise-test-coverage`.
- 릴리스 diff 로 영향 범위 산정 → `diff-driven-test` 로 범위를 낸 뒤 이 스킬로 TC 를 쓴다.
- 함수 단위 회귀 방어 → `write-unit-tests`.

## 출력 계약

`references/TEMPLATE.md` 구조:
1. **근거 목록** — 문서 판, 코멘트 날짜, 커밋, 실행 화면 캡처 목록(또는 「캡처 못 함 — 이유」).
2. **TC 표** — 표 머리(Summary, 공통 안내 한 곳) + 템플릿 열 전부.
3. **부록 note** — 행별 기술 정보(시트에 안 들어감).
4. **기획·코드 차이 / `[확인 필요]` / 가정 목록**.
5. **반증 라운드 기록** — (a) 라운드별 ✅/⚠/❌ 수, (b) 라운드별 가능/모호/불가/도구 한계 수와 Pre 반례 검사한 행 수, 고친 것.
6. **lint 결과** — 마지막 줄 그대로와 종료 코드.
