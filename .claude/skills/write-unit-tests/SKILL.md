# write-unit-tests — 코드베이스 유닛 테스트 작성

대상 코드의 계약을 파악해 **버그를 실제로 잡는** 유닛 테스트를 짜는 방법. 초록불 채우기가 아니라 **회귀 방어망**을 만드는 것.

## 좋은 산출물이란 (품질 기준)

- 테스트가 **실제로 실패를 잡는다**(로직 깨면 red). green 채우기용 tautology 아님.
- 정상 1 + **경계·예외 N**(빈값/최대/null/에러/타임아웃). 가치는 예외에.
- repo **관례를 따른다**(프레임워크·파일 위치·네이밍·mock 방식). 새 스타일 강요 안 함.
- 테스트 이름이 **의도를 말한다**(`returns_zero_when_cassette_empty` 식).
- 외부 의존(HW/네트워크/시계/랜덤)은 **격리**(mock/fake/고정값). 결정적(deterministic).

## 절차

1. **헌법·상태 로드**: `QA_ENGINEER_CONTEXT.md` + `state/qa-engineer-focus.md`.
2. **repo 관례 파악**: 테스트 프레임워크·기존 테스트 위치·mock 패턴을 실제 파일로 확인. (vitest/pytest/gtest 등 — 추측 말고 확인)
3. **대상 계약 파악**: 함수/모듈의 입력·출력·부작용·에러 경로를 소스로 읽는다. 스펙 애매하면 표시(TBD).
4. **케이스 설계** (`advise-test-coverage` + `TC_DESIGN_GUIDE.md §5`):
   - 정상(대표 1) + EP 무효클래스 + BVA 경계 + 에러/예외 경로 + 상태전이.
5. **테스트 작성**: repo 관례대로. 외부 의존 격리. AAA(Arrange-Act-Assert) 구조. 단언은 **구체적**(값·에러타입·호출횟수).
6. **실행 → 통과 확인**: 실제로 돌린다. green 확인.
7. **역검증(必)**: 대상 로직을 **일부러 한 줄 깨서** 테스트가 red 되는지 본다. red 안 되면 그 테스트는 무의미 → 다시. (검증 후 원복)
8. **보고**: 무엇을 커버했나 / 무엇을 못 했나(`N/T`) / 발견한 의심점(버그 단정 X, 스펙 확인 권고).

## 언제 쓰지 말 것 (경계)

- E2E/통합/브라우저 UI 자동화 → 키오스크 런타임 프레임워크·Playwright 스코프.
- 스펙 자체가 미정 → 먼저 `advise-test-coverage` 로 조언, 스펙 확정 후 테스트.
- 테스트 통과 위해 프로덕션 코드 수정 요청받음 → 그건 개발자 세션. QA 는 테스트까지 + 의심점 보고.

## 출력 계약

`references/TEMPLATE.md` 구조:
1. **대상·프레임워크** — 무슨 모듈, 무슨 테스트 러너, 파일 위치.
2. **케이스 목록** — 이름 / 무엇을 검증 / 정상·경계·예외 구분.
3. **테스트 코드** — repo 관례대로(코드 언어 OK).
4. **실행 결과** — pass/fail 실제 출력. 역검증(깨면 red) 확인 여부.
5. **커버 못 한 것 / 의심점** — `N/T` + 스펙 확인 권고(버그 단정 금지).

품질 앵커: `references/EXAMPLE.md`. **NEVER** 단언 약화·테스트 삭제로 green 만들기.
